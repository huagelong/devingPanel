# devingPanel 需求文档

> 版本：v0.2（评审修订）
> 日期：2026-10-24
> 状态：需求与页面设计阶段，未进入编码

---

## 1. 背景与问题

### 1.1 现状痛点

目前的 VPS 上使用了一款带编译、部署功能的 Docker 管理软件，存在以下问题：

| 问题 | 说明 |
|------|------|
| **资源浪费** | 管理软件常驻运行，平时几乎不被使用，却持续占用 VPS 的 CPU / 内存 |
| **编译抢占生产资源** | 项目上线前在 VPS 上执行编译，编译期间的 CPU / 内存 / 磁盘 IO 高峰直接影响线上服务 |
| **单机操作** | 一个项目涉及多台 VPS 时，需要逐台登录、逐台部署，重复劳动且容易出错 |
| **职责错位** | 编译本质是"开发侧"的工作，却发生在"生产侧"的机器上 |

### 1.2 核心思路（第一性原理）

- **编译应该在资源最充裕的地方进行**：开发机通常配置远高于 VPS，编译应回到开发机。
- **生产环境只应承担运行职责**：VPS 只需要接收现成的镜像并启动容器。
- **常驻软件应为零或接近零**：VPS 上不装管理后台，优先复用已有的 SSH 通道。
- **重复的操作应收敛为一个动作**：多台 VPS 的发布，在客户端应表现为"一键"。

由此得出产品定位：

> **devingPanel 是一款运行在开发机上的跨平台客户端，负责在本地构建 Docker 镜像、将镜像分发到一台或多台 VPS 并完成远程部署；同时提供轻量的 VPS 资源监控与 Docker 容器管理能力。VPS 侧保持极简，不需要额外安装常驻管理软件。**

## 2. 目标与非目标

### 2.1 目标

1. 将项目编译与镜像构建从 VPS 迁移到开发机，消除上线时的 VPS 资源争抢。
2. 支持 Windows / macOS / Linux 三大桌面平台作为客户端运行环境。
3. 支持一台 VPS 的单项目部署（MVP）。
4. 支持一个项目同时部署到多台 VPS（一键发布）。
5. 提供基本的 VPS 资源监控（CPU / 内存 / 磁盘 / 网络）。
6. 提供基本的 Docker 容器 / 镜像管理能力（查看、启停、重启、删除、查看日志）。
7. VPS 侧除 Docker Engine 和 SSH 外，**不强制安装任何额外软件**。

### 2.2 非目标（当前版本明确不做）

以下内容当前阶段不做，避免过度设计；若未来确有需求再演进：

- 不做 Web 端管理后台（客户端本身就是管理界面）
- 不做团队协作 / 多用户 / 权限体系（单开发者或小团队可直接共用配置）
- 不做 CI/CD 流水线编排（触发方式以 GUI 手动一键为主）
- 不做 CLI 形态（只提供 GUI 客户端）
- 不做 Kubernetes 支持（明确以 Docker / Docker Compose 为目标运行时）
- 不提供自建镜像仓库托管（可选对接外部 Registry）
- 不做灰度发布 / A-B 流量切分（只保证"逐台更新 + 健康检查"的滚动式发布）

## 3. 用户与使用场景

**目标用户**：独立开发者 / 小团队，管理 1~10 台 VPS，项目以 Docker 化的 Web 服务为主。

### 典型场景

1. **日常开发**：开发机运行客户端，可随时查看 VPS 状态与容器运行情况。
2. **发布上线**：在开发机改完代码，客户端一键"构建、推送、部署"到一台或多台 VPS。
3. **多 VPS 项目**：同一项目服务部署在多台 VPS 上，客户端默认按顺序逐台更新；尽量降低影响，但不承诺零停机（取决于上游流量分配、剩余节点容量及应用健康检查）。
4. **线上排查**：客户端查看容器日志、重启异常容器、查看资源占用，无需 SSH 客户端。
5. **回滚**：发布失败或线上异常时，若该主机仍保留上一已完成版本，可回滚。

## 4. 功能需求

功能按优先级分阶段，P0 为 MVP 必备，P1 / P2 为后续迭代。

### 4.1 VPS 主机管理（P0）

| 编号 | 需求 | 说明 |
|------|------|------|
| H-1 | 添加 / 编辑 / 删除 VPS | 记录别名、IP / 域名、SSH 端口、认证方式（密码 / 私钥）、登录用户 |
| H-2 | 连接测试 | 添加时即可一键测试 SSH 连通性与 Docker 可用性 |
| H-3 | 主机分组 | 按"项目"或"环境"组织 VPS（例如 `myapp-prod` 组含 3 台机器） |
| H-4 | 认证凭据安全 | 密码 / 私钥等凭据按 SEC-1 存入操作系统凭据管理器，不明文写入配置文件或数据库 |

### 4.2 本地镜像构建（P0）

| 编号 | 需求 | 说明 |
|------|------|------|
| B-1 | 关联项目 | 项目 = 本地代码目录 + Dockerfile + 构建参数 |
| B-2 | 一键构建 | 在开发机调用本地 Docker Engine 执行 `docker build` |
| B-3 | 构建参数配置 | 支持配置镜像 tag 规则、build args、目标平台；默认根据目标主机架构自动选择并在开发机为每种架构各构建一次 |
| B-4 | 构建日志实时输出 | 客户端实时展示构建过程与结果 |
| B-5 | 依赖检测 | 检测开发机 Docker 环境（Docker Desktop / OrbStack / 原生 Docker）是否可用，给出明确指引 |

### 4.3 镜像分发（P0）

| 编号 | 需求 | 说明 |
|------|------|------|
| T-1 | 直连传输（默认） | `docker save` 压缩后通过 SSH/SFTP 传输，远端 `docker load`。无需任何外部 Registry |
| T-2 | Registry 传输（可选） | 若用户配置了 Docker Registry（Hub / GHCR / 阿里云 ACR / 私有仓库），可改用 push + 远端 pull 的标准方式 |
| T-3 | 传输进度 | 直连模式显示每台 VPS 的传输进度与耗时；Registry 模式显示每架构 push 进度和每台 VPS 的拉取进度与耗时 |
| T-4 | 失败处理 | 传输失败时给出原因（网络 / 认证 / 磁盘不足），允许对该主机重试当前阶段；部署状态不明时须先核实远端状态，不盲目重跑 |

> **设计决策**：直连传输是默认方式，因为它对"个人 VPS + 私有项目"最友好：零外部依赖、零额外费用。Registry 模式作为可选能力保留给已有仓库的用户。

### 4.4 远程部署（P0）

| 编号 | 需求 | 说明 |
|------|------|------|
| D-1 | Compose 驱动部署 | 项目可配置一个或多个 compose 文件路径，按顺序交给 `docker compose` 原生合并；目标服务使用本次本地构建镜像，其他服务可使用 VPS 已有或可拉取的现成镜像；发布前禁止所有服务远端构建，上传并保持相对路径结构 |
| D-2 | 一键部署 | 单 VPS：构建、推送、远端 `docker compose up -d` |
| D-3 | 环境变量注入 | 支持按"项目 x 目标主机"配置环境变量，部署时写入 `.env` 文件（权限 600） |
| D-4 | 健康检查 | 单主机可检查容器运行状态并标注"未验证就绪"；多主机滚动发布在本地构建后检查镜像或 Compose 是否提供有效的 Docker HEALTHCHECK，逐台健康后才进入下一台 |
| D-5 | 部署历史 | 每次发布记录：时间、发布标识、每台 VPS 的实际架构与镜像 tag、结果、耗时；可在客户端查看 |
| D-6 | 回滚 | 每台主机独立记录已完成版本（镜像标识、Compose 文件、环境配置，含单主机"已启动但未验证就绪"）；保留最近 N 个已完成版本（N 可配置，至少 1），N=1 时无上一版本可回滚并明确提示；有上一版本时按主机恢复并重新检查状态 |
| D-7 | 历史镜像清理 | 仅清理由客户端管理且超出保留数量的历史镜像及其版本化部署目录（含 Compose 与 .env）；定期清理，保护当前运行和可回滚版本，避免占满 VPS 磁盘 |

### 4.5 多 VPS 一键发布（P1）

| 编号 | 需求 | 说明 |
|------|------|------|
| M-1 | 项目绑定多主机 | 一个项目可关联多台 VPS（来自同一主机组） |
| M-2 | 顺序滚动更新 | 默认**逐台**执行：在开发机为每种目标架构各构建一次；每台使用匹配架构镜像部署，健康检查通过后再处理下一台。失败则暂停后续发布 |
| M-3 | 并行度可配置 | 默认 1；大于 1 时分批执行，每批全部通过健康检查才开始下一批；失败后不启动新批次，已启动的任务继续至可确认状态 |
| M-4 | 失败可继续 | 中途失败时，可选择"跳过该台继续发布剩余机器"，或终止发布 |
| M-5 | 发布总览 | 发布过程展示每台机器的状态（等待 / 传输中 / 部署中 / 成功 / 失败） |

### 4.6 VPS 资源监控（P1）

| 编号 | 需求 | 说明 |
|------|------|------|
| S-1 | 实时概览 | CPU 使用率、内存使用率、磁盘使用率、网络吞吐 |
| S-2 | 数据获取方式 | 通过 SSH 执行轻量命令（如 `docker stats --no-stream`、`free`、`df`）或复用 Docker API，**不在 VPS 上安装 agent** |
| S-3 | 历史趋势（P2） | 本地（客户端侧）轮询并保存历史数据，绘制趋势图 |
| S-4 | 告警（P2） | 阈值告警（如 CPU > 90% 持续 5 分钟），通知方式：客户端内提醒 / 系统通知 |

> **设计决策**：监控数据在客户端本地拉取与存储，不在 VPS 上落任何数据。历史趋势依赖客户端在线，不追求 7x24 完整监控，这超出了"开发机客户端"的定位。

### 4.7 Docker 容器 / 镜像管理（P1）

| 编号 | 需求 | 说明 |
|------|------|------|
| C-1 | 容器列表 | 展示 VPS 上所有容器：名称、镜像、状态、端口映射、CPU / 内存占用 |
| C-2 | 容器操作 | 启动 / 停止 / 重启 / 删除容器 |
| C-3 | 容器日志 | 查看容器实时日志（`docker logs -f`）与历史日志 |
| C-4 | 镜像列表 | 展示镜像列表，支持删除无用镜像（`docker image prune`） |
| C-5 | 磁盘清理 | 提供独立的全局 Docker 清理操作；执行前展示预估可回收空间及将影响其他项目的范围，明确确认后才可执行，不与 D-7 的项目历史镜像清理混用 |

### 4.8 安全（P0 贯穿）

| 编号 | 需求 |
|------|------|
| SEC-1 | SSH 凭据（密码 / 私钥）及敏感环境变量存入操作系统凭据管理器（Windows Credential Manager / macOS Keychain / Linux Secret Service），SQLite 只存引用；无可用安全存储时提示设置，不退回明文；首次连接须确认 SSH 主机指纹，指纹变化时阻断并要求核对 |
| SEC-2 | 客户端与 VPS 的所有通信仅走 SSH，不额外开放网络端口 |
| SEC-3 | 部署操作写入本地审计日志（何时、对哪台机器、做了什么） |
| SEC-4 | 推送到 VPS 的 `.env` 等敏感文件权限设为 600，属主为 SSH 登录用户 |
| SEC-5 | 本机界面锁屏：可设置、修改及关闭密码，手动锁屏，并设置无操作自动锁屏间隔（预设 1/5/15/30/60 分钟或自定义 1–1440 分钟，默认 5 分钟）；锁定后及重新打开客户端时需密码解锁。修改密码、关闭锁屏或修改间隔需验证当前密码。密码不以明文保存；本机存储或加密能力不可用时不临时启用或明文降级。锁屏仅保护界面操作，不替代 OS 登录、磁盘加密及服务器认证。 |

### 4.9 客户端配置备份与恢复（新增页面需求）

| 编号 | 需求 | 说明 |
|------|------|------|
| BK-1 | 本地配置导出 / 导入 | 备份主机、项目、非秘密设置，使用带格式版本的密码加密 JSON；导入先解密校验再预览、明确确认整体覆盖；不包含 VPS 业务数据、镜像、容器卷及回滚材料 |
| BK-2 | S3 配置备份页面 | 配置 S3 / S3 兼容服务的 Endpoint、Region、Bucket、Prefix 与 Path-style；提供连接测试、创建备份、备份记录、下载、预览恢复和删除入口 |
| BK-3 | 备份安全与恢复约束 | 不导出密码、私钥、令牌、环境变量值和构建参数值；运行中/待核实任务禁止导入；恢复后重新确认主机信任和项目配置，不能把配置备份当作可执行的回滚材料 |
| BK-4 | 备份加密密码 | 本地与 S3 备份均必须用用户设置的密码加密；设置时二次确认，恢复时输入原密码，密码错误或文件被篡改拒绝恢复；密码不随文件保存，忘记无法找回；不提供明文降级 |

当前仅实现 HTML 页面和本地配置 JSON 交互，S3 上传及系统凭据管理器接入留待桌面实现阶段；原型必须明确标注模拟行为。

## 5. 非功能需求

| 维度 | 要求 |
|------|------|
| **平台** | 客户端支持 Windows 10+ / macOS 15+ / 主流 Linux 桌面（X11 / Wayland） |
| **VPS 环境** | 仅要求 VPS 已安装 Docker Engine（含 compose 插件）并开放 SSH |
| **性能** | 客户端自身常驻内存不超过 200 MB；空闲时 CPU 占用接近 0 |
| **可靠性** | 部署过程中断（如网络闪断）时，客户端重新连接后核实远端部署状态并展示"成功 / 失败 / 待核实"；未核实前不得宣称完成或自动重试部署 |
| **易用性** | 首次使用：添加 VPS、关联项目、一键发布，三步内完成核心流程 |
| **国际化** | 当前支持简体中文和英语，默认中文；在设置中切换并保存本机语言偏好。覆盖导航、表单、弹窗、状态提示及备份/加密交互，不翻译用户数据、技术标识或原始日志，不改变业务状态及备份格式 |
| **本地存储** | 主机、项目、部署历史等数据使用 SQLite 存储（单文件、零部署成本） |

## 6. 关键技术思考（供设计阶段参考）

本节仅记录需求分析阶段的技术判断，**具体选型在架构设计文档中确定**。

### 6.1 本地构建环境

开发机需要本地 Docker Engine：

- Windows：Docker Desktop
- macOS：Docker Desktop 或 OrbStack
- Linux：原生 Docker

客户端启动时探测本地 Docker 可用性；不可用时给出平台化的安装指引。**第一版不实现"无 Docker 的远程构建"**，那会显著增加复杂度。

### 6.2 与 VPS 的通信方式

**核心决策：仅依赖 SSH，不在 VPS 上安装任何 agent 或常驻服务。**

- 好处：VPS 零额外占用（正是本次要解决的痛点）；无新增攻击面（不开放新端口）；有 SSH 权限即可用，上手零成本。
- 代价：实时性略受限（每次交互都要建 SSH 会话，可通过连接复用缓解）；容器日志 / 终端类交互功能走 SSH 流式转发，实现复杂度略高。

这两点代价在"开发机客户端"的场景下完全可接受。

### 6.3 镜像分发的默认策略

直连（save / 传输 / load）不依赖外部 Registry，但耗时取决于本地上行、VPS 带宽、压缩率与镜像大小；界面展示真实传输进度，不预设小镜像一定能在数秒内完成。有现成 Registry 时可选 push / pull 模式。

### 6.4 多 VPS 部署的顺序性

多台 VPS 服务同一项目时，默认**逐台**进行且每台通过健康检查后才进入下一台。并行度大于 1 时按批处理，失败停止后续批次；逐台发布只能降低中断风险，不能在没有流量摘除能力的情况下保证零停机。

已确认：发布期间**不需要处理上游 LB 的节点摘除**，客户端不做任何 LB / 反向代理联动。

## 8. 决策记录

### 8.1 已确认决策（2026-10-24）

1. **反向代理 / LB**：发布期间不处理 LB 摘除节点，客户端不做任何 LB 联动。
2. **回滚保留策略**：远端历史版本保留数量可由用户设置，并定期清理；客户端在线时检查超额的托管镜像，离线期间下次启动/重连后补做检查；不安装 VPS 定时服务。
3. **配置文件组织**：主机、项目、部署历史使用 SQLite 存储。
4. **CLI 形态**：不做，只提供 GUI 客户端。
5. **compose 文件约定**：项目可配置一个或多个 compose 文件路径，部署时按顺序传给 `docker compose` 由其自行合并（如 `base.yml` + `prod.yml` 覆盖式组合）；客户端不实现自定义合并逻辑，单文件项目同样适用。首版要求文件在项目目录内；相对路径与文件依赖的限制见页面设计。
6. **客户端 macOS 最低版本（2026-10-25）**：提高到 macOS 15+，与当前 GPUI Kit 安装要求一致；仍需在 macOS 15 实机验证构建、运行与打包。

### 8.2 实现约束（非用户原话）

- 保留数量允许设为 1，以节省空间；该主机将失去回滚到上一版本的能力，界面必须明确警告。默认保留 3 个。
- 多架构主机一次发布按架构在本地分别构建镜像；本地 Docker 不支持某种目标平台时在传输前失败，并给出构建环境指引。
- 首个 Compose 文件必须在项目根目录；这保证多文件合并时的相对路径和生成的 `.env` 在开发机与 VPS 上使用同一基准目录。
- 每次发布在 VPS 使用独立的版本化部署目录存放 Compose 与 `.env`；版本退出保留期时，清理流程同步删除该目录，回滚所需材料以客户端本地保存为准。
