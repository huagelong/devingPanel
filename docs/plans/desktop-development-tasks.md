# devingPanel 桌面客户端开发任务计划

> 状态：待实施。2026-11-11 基线：`dev` 仅跟踪 `.gitignore` 和 `LICENSE`，没有 Go 源码；`docs/` 与 `AGENTS.md` 按约定只保留在本机，不纳入版本控制。`docs/webui` 的 90 个 Playwright 测试在本机通过，但只覆盖浏览器原型，不代表桌面客户端或真实 VPS 验收通过。

## 目标与边界

- 首个可用版本（P0）让用户在本机管理主机和项目，完成一台隔离主机的真实 Docker Compose 发布、结果核实、历史查看和可用版本回滚。
- P1 在 P0 的稳定执行链路上增加多主机批次与容器管理；P2 再加入趋势和告警。Registry、S3 等能力按实际优先级独立交付，不阻塞默认的 SSH 直传路径。
- 正式客户端采用 `docs/technical-architecture.md` 拟定的 Go + MyGo 原生 UI。VPS 只需要 SSH、Docker Engine 和 Docker Compose，不安装本产品的服务或 agent，不在 VPS 构建镜像。MyGo 及插件能否满足目标平台要求，必须先通过技术验证，不能把文档中的拟定能力当作已验证事实。
- `docs/webui` 是页面设计和主要交互的对照基准。正式客户端逐页对照其布局、组件、文案、状态与窄窗口表现；真实数据和系统权限由桌面端实现，原型中的演示行为不能照搬为真实执行结果。页面细节同时参照 `docs/design/00-overview.md` 至 `06-settings.md`。

## 执行规则

- 按下表顺序推进。每项只有在交付物、自动化检查和需要的实机证据齐全后才标记完成；失败或未验证写明原因，不用原型演示代替实机结果。
- 每个阶段形成一个可运行版本。优先完成真实单主机闭环；多主机、监控和云备份不提前塞进 P0 的核心执行路径。
- 所有 VPS 测试使用专门的隔离项目、目录和容器；仅清理本次测试明确创建的资源。断线或远端结果不明时保留记录并等待核实，不自动重试或清理。
- 页面实现须与 `docs/webui` 一致。发现原生平台限制时，记录具体差异并取得用户确认后再调整；把确认结果和验收证据更新到本计划及对应设计文档。`docs/` 不纳入 Git 的约定不因更新文档而改变。

## 任务清单

### 0. 技术选型与可运行骨架（P0 前置）

- [ ] **T00-1 MyGo 能力验证**：固定可复现版本，验证原生窗口、路由/状态、对话框、目录选择、系统凭据、SQLite 插件与后台任务；记录实际 API、限制和版本。优先在 Windows 验证，再分别验证 macOS、Linux 的构建、启动及打包。
- [ ] **T00-2 最小应用骨架**：创建 Go 模块、入口、应用数据目录、错误报告和基础 CI；窗口能启动、切换页面并显示本地 Docker 可用状态。保持 UI、业务流程和 SSH/文件/数据库访问的职责清楚，不预建庞大框架。
- [ ] **T00-3 页面基线**：按 `docs/webui` 建立 App Shell、主题、语言、通用表格/表单/弹窗、加载/空/错误状态；逐页核对原型，无法一致的具体项目先提交用户确认。

**阶段验收**：三平台可构建并启动一个可导航的原生窗口；凭据和 SQLite 的关键读写及失败行为有实测记录。若 MyGo 关键能力不满足要求，先重新评估技术选型，再继续业务实现。

### 1. 本地数据、主机与项目配置（P0）

- [ ] **T01-1 本地持久化**：建立 SQLite 表和迁移，保存主机、项目索引、非秘密设置、发布任务与历史；事务失败不留下半写状态。页面打开读取本地数据，写入后立即刷新，后台刷新不覆盖未提交表单。
- [ ] **T01-2 凭据与主机信任**：使用系统凭据管理器保存 SSH 秘密；验证超限秘密的加密文件方案和凭据管理器不可用时的阻断行为。首次连接展示 SHA256 指纹供独立核对，指纹变化阻断连接；支持文档规定的认证和连接方式，按实际使用顺序实现。
- [ ] **T01-3 主机页面**：实现新增、编辑、分组、连接测试、状态和详情。对照 WebUI 的主机列表、表单、指纹确认、错误提示以及窄窗口布局。
- [ ] **T01-4 YAML v2**：读取、严格校验和原子保存项目目录的 `devingpanel.yaml`；检查文件大小、字段、相对路径、构建服务、Compose 文件与目标绑定。编辑期间发生外部修改时拒绝覆盖；发布前再次读取，不用 SQLite 中的旧配置兜底。
- [ ] **T01-5 项目页面**：实现创建/导入、构建配置、Compose、环境变量、目标主机和历史入口。敏感值只存凭据系统；Build args 明确为非秘密。项目以不可变 ID 关联历史。

**阶段验收**：重启后配置完整；未信任、凭据缺失、文件损坏和外部修改均阻断相应操作且提示可理解；项目表单与 WebUI 对应页面逐项核对。

### 2. 单主机真实发布（P0 核心路径）

- [ ] **T02-1 发布前预检**：冻结本次 YAML 和目标；检查本地 Docker/Buildx、目标架构和远端 Docker/Compose、SSH 信任、Compose 合并结果、变量与镜像 tag 冲突。任何预检失败都不上传或启动远端服务。
- [ ] **T02-2 本机构建与传输**：按目标架构在本机构建，导出镜像归档，通过 SFTP 上传并在目标机 `docker load`；记录阶段、进度和明确的失败原因。复用已验证 SSH 连接，不把凭据、环境变量值或完整 Compose 输出写入日志。
- [ ] **T02-3 远端部署与健康核对**：上传 Compose 文件和权限为 600 的 `.env`，以固定项目名执行 Compose；执行前核对解析后的镜像引用，拒绝远端 `build`。有 HEALTHCHECK 才标记健康成功；无 HEALTHCHECK 显示“已启动，未验证就绪”。
- [ ] **T02-4 持久化执行状态**：保存任务、阶段、日志、目标身份和结果。断线、超时、退出或回执不明时写入“待核实”，禁止自动重试；重新连接后依据远端证据核对。客户端重启后仍能找到未结束任务并进入核实流程。
- [ ] **T02-5 发布页面与历史**：对照 WebUI 的执行/历史、逐主机行、日志、失败处置和窄窗口表现；历史保存当时的项目及配置快照，项目改名后记录归属不变。

**阶段验收**：隔离的单台 VPS 完成一次成功发布；预检失败、构建失败、上传中断、Compose 失败、健康失败和客户端重启分别留下正确状态与可核实证据。不能只凭 UI 进度判定发布成功。

### 3. 回滚、保留与 P0 收口

- [ ] **T03-1 版本材料**：为可回滚版本保存本机归档和远端 Compose/环境材料的引用及校验信息；材料缺失时禁用回滚并说明原因。
- [ ] **T03-2 单主机回滚**：核对主机信任、Docker 身份、镜像与版本材料，二次确认后执行回滚并保存独立结果；不重新构建，也不改写原发布记录。
- [ ] **T03-3 精确清理**：按项目和主机的保留策略列出候选，确认当前版本及其他引用后只删除受托管的准确 tag、版本目录和本机材料；远端结果不确定时留待核实，不运行全局 prune。
- [ ] **T03-4 P0 交付验证**：完成桌面与窄窗口页面核对、中文/英文关键路径、三平台构建/启动和安装包验证；在受控环境验证发布、重启恢复与回滚。

**P0 完成门槛**：用户可从新建主机和项目一路操作到真实发布、查看持久化历史、核实异常并回滚可用版本；无秘密明文落盘或进入日志的已知路径。

### 4. 多主机批次（P1）

- [ ] **T04-1 批次模型**：保存目标顺序、并行度、传输方式、架构、构建产物、逐主机阶段和结果；同架构共享构建产物。先实现顺序批次，再验证并行波次。
- [ ] **T04-2 混合架构预检与构建**：为目标架构分别构建并核对镜像；目标架构、Docker daemon 或配置发生变化时阻断继续，不能向错误目标发布。
- [ ] **T04-3 失败与未知处置**：已知失败允许针对该主机重试、跳过或终止；结果不明必须先核实。终止只取消未开始目标，已进入远端操作的目标等待明确结果或“待核实”。
- [ ] **T04-4 批次页面与验收**：对照 WebUI 的逐主机状态、日志、历史、失败处置和窄窗口布局；在两台隔离主机上验证顺序、并行、断线、客户端重启及混合架构。

**P1 多主机开放门槛**：真实两主机执行和异常核实通过，界面在执行与失败时可读、可操作，历史准确。门槛未完成前正式“开始发布”入口保持禁用。

### 5. 运维与可选能力（按需逐项排期）

- [ ] **T05-1 容器管理**：复用 SSH/Docker 能力实现容器、镜像、日志和明确范围的操作；每个破坏性操作先展示目标并二次确认。
- [ ] **T05-2 主机资源与趋势**：先实现有明确数据来源和刷新语义的资源数据；趋势和告警作为 P2 独立验收。
- [ ] **T05-3 Registry 传输**：在默认直传稳定后实现凭据、推送、远端拉取和中断核实；任务创建时冻结传输方式。混合架构 tag、临时认证目录和泄露风险逐项验证。
- [ ] **T05-4 配置备份与锁屏**：先交付真实本地加密导出/恢复，再评估 S3；恢复后重新确认主机信任和项目配置。锁屏覆盖启动、手动及空闲超时，不声称替代操作系统安全。

## 跨阶段验收清单

- UI：每个已交付页面与 `docs/webui` 对照，检查桌面和窄窗口的布局、组件、主要交互、加载/空/错误状态、主题及中英文；任何差异须有用户确认记录。
- 自动化：Go 格式、静态检查和单元测试；YAML 校验、状态转换、数据库迁移和预检规则使用不触碰 VPS 的测试；原型 Playwright 测试只作为设计回归参考。
- 实机：真实 SSH 指纹、Docker/Compose、构建产物、健康结果、断线恢复和回滚均保留命令/日志/状态证据；三平台安装包至少完成启动验证。
- 发布：只按实际通过的阶段声明能力。P0 单机通过不等于 P1 多机通过，原型测试通过也不等于真实部署验收通过。
