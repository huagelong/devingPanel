# P3 项目列表 / 项目详情 设计文档

> 需求映射：B-1 项目关联、B-3 构建参数、D-1 多 compose 文件、D-3 环境变量（SEC-4 写入远端 .env 权限 600）、M-1 绑定多主机

## 1. 页面目的

管理"项目"：本地代码目录、Dockerfile、compose 文件、构建参数、环境变量与目标主机的绑定关系。项目是发布的最小单元。

## 2. 入口

- 侧边栏"项目"；发布页选择项目。

### 3.3 导入开发者配置的项目

项目列表 [导入已配置项目] 选择包含 `devingpanel.yaml` 的本地代码目录。项目导入后可在 devingPanel 的构建、Compose 和目标主机页签编辑，保存结果写回项目文件；也可导入已有文件。YAML 不存 SSH 密码、私钥或敏感环境变量；管理员须在本机预先配置目标主机、可信指纹和凭据。缺失时项目仍可导入，但显示“需管理员处理”并阻断发布。

```yaml
version: 2
name: myapp
tag: "{timestamp}"
builds:
  - service: web
    dockerfile: Dockerfile
    image: myapp
    platform: auto
    args:
      NODE_ENV: production
deploy:
  compose:
    files: [compose.yaml, compose.prod.yaml]
  targets:
    - group: prod
      host: web-1
```

项目根目录是所有构建的 build context；每个 `builds` 条目须有唯一服务、镜像名及镜像变量，Compose 对应服务使用 `${DEVINGPANEL_IMAGE_WEB}` 等变量。Dockerfile 与 Compose 文件均为目录内相对路径，首个 Compose 文件在根目录。目标按 YAML 顺序发布，同组 `group/host` 必须在本机唯一匹配；变更目标绑定时需管理员明确确认，可能清理取消绑定主机的本地专属变量。文件最大 64 KiB、UTF-8、单文档、`version: 2`，重复/未知字段、非法路径或格式一律报错；v1 清单需由开发者升级。Build args 是明文，不可填写秘密。界面保存前校验完整清单与文件路径；若文件在编辑期间被外部修改则拒绝覆盖，需 [重新读取配置]。发布前再读取并冻结快照，不使用过期界面数据。文件丢失/损坏时不回退 SQLite 的旧值。

正式桌面客户端以 `devingpanel.yaml` 作为项目构建与部署配置，不为已删除的旧表单实现保留兼容层。项目由列表导入或新建后配置，其构建/Compose/目标配置由界面编辑并写回 YAML，敏感环境变量仍在本机安全存储。多主机批次按目标顺序和并行度分波次执行；每波健康结果须逐目标确认，故障与未知状态在历史页单独核实。正式多主机 [开始发布] 在实机、视觉和混合架构验收完成前禁用。

### 4.1 布局

```
内容区
|

|
```

YAML 项目在前三个技术配置页签中编辑同一份表单状态，各页签均有 [保存到 devingpanel.yaml]。构建页可增删、排序多个服务及其 Build args；Compose 页按顺序编辑文件；目标页按顺序编辑本机唯一的主机组/别名。保存校验完整配置并原子替换文件；目标绑定变化后仍需管理员确认。环境变量沿用本机存储，不写入 YAML。

```text

Compose   [文件 1] [文件 2] [添加文件] [保存]
目标主机  [主机组 / 别名] [添加目标] [保存] → 变更时确认绑定
```

### 4.2 Tab: 构建配置

`devingpanel.yaml` v2 项目按 4.1 节编辑有序 `builds` 列表，每个服务各有 Dockerfile、镜像、平台和 Build args；不得把多个服务压成一个“部署服务”选择值。WebUI 在用户授权项目目录后实际读写 YAML 文件；远端构建和发布仍为演示。

Card 表单：

| 字段 | 控件 |
|------|------|
| 构建服务 | 有序列表；每项包含唯一服务名、Dockerfile 相对路径和镜像名 |
| Tag 规则 | Input (mono)，支持 `{timestamp}` `{git-sha}` 占位，默认 `{timestamp}`；仅选择 `{git-sha}` 的项目需要 Git 仓库，生成发布标识后附架构后缀，构建前检查 tag 冲突，绝不覆盖旧版本 |
| 目标平台 | 每个构建项可选按主机自动（默认）/ linux/amd64 / linux/arm64；手选平台时所有已选主机必须匹配 |
| Build args | 每个构建项独立的 Key-Value 编辑列表（Add row） |

底部 [保存]；保存后 Toast 反馈。
正式客户端在使用 `{git-sha}` 时由内置 Go 库读取项目所属仓库的 `HEAD`，不要求本机安装 Git；普通非 Git 项目可正常使用默认 `{timestamp}`。若所选项目不是 Git 仓库或尚无提交，发布前提示修改 Tag 规则，不自动改用时间戳。`HEAD` 不包含未提交改动，预检时提示用户核对工作区。WebUI 原型仍只显示示例 SHA。
发布前通过 SSH 读取每台目标主机架构；自动模式汇总所需平台（如 `linux/amd64`、`linux/arm64`），客户端在开发机为每种架构各构建一次，为同一发布标识生成不同镜像 tag（如 `myapp:20261024-120000-amd64` 与 `myapp:20261024-120000-arm64`），同架构主机复用镜像。手选平台不匹配或本地 Docker 无法构建任一目标平台时，在上传前失败并提示本地构建环境需要的能力，不回退到 VPS 编译。Build args 不是秘密传输机制，编辑区提示不要填写密码或令牌。


交互：调整顺序用上移/下移按钮；文件不存在于本地时行内 warning 提示"文件不存在"。

发布约定（MVP）：

YAML v2 项目使用 3.3 节定义的服务专属镜像变量，如 `DEVINGPANEL_IMAGE_WEB`；每个 `builds` 项对应一个 Compose 服务和镜像变量。

- 允许一个或多个位于项目目录内的 Compose 文件，但**首个文件必须直接位于项目根目录**；后续文件可位于子目录。上传时保持相对于项目根目录的路径，开发机与 VPS 均以项目根目录为 Compose project-directory，固定 Compose 项目名，避免每次发布生成新的服务栈。生成的 `.env` 位于该次发布的版本化部署目录根（以项目根目录为基准），`env_file: .env` 因此按首文件所在根目录解析。
- 每个构建服务须通过自己的 `DEVINGPANEL_IMAGE_<服务名>` 变量引用本地构建镜像；客户端为每台主机填入匹配架构的镜像 tag（直连时为本地镜像名，Registry 模式为完整仓库地址）。其他服务可使用 VPS 已有或可拉取的现成镜像；部署前检查这些镜像是否可获取，缺失且无法拉取则报错，不因缺失而在 VPS 构建。
- `.env` 文件本身不能保证插值优先级：调用本地和远端 Compose 时，客户端必须从继承的进程环境中移除项目配置键与保留键，再以 `--env-file` 显式指向本次版本化根目录的 `.env` 提供项目值；服务专属镜像变量由客户端设置为该主机预期 tag，不能从用户环境继承。构建前与远端 `up -d` 前分别解析最终配置，确认所有构建服务的 `image` 均精确等于该主机预期 tag；配置原文可能含密钥，只在内存中校验且不得记录到日志。
- 发布前在每台主机对应环境变量下验证合并结果：所有服务都不得包含 `build`，否则阻止发布，避免 VPS 编译。仅上传 Compose 文件和客户端生成的 `.env`；普通相对 bind mount、除 `.env` 外的 `env_file`、本地文件型 `configs` / `secrets`、`include` / `extends` 及项目外路径不支持首版远端部署，检查到即明确报错；Windows 本地绝对路径不可作为 VPS 挂载路径，远端绝对挂载路径须由用户预先准备。不要静默改变路径指向。
- `.env` 仅提供 Compose 变量插值；要将变量注入容器，Compose 服务须在 `environment` 显式引用变量，或使用 `env_file: .env`。预览仅展示脱敏摘要，绝不直接展示可能含密钥的 `docker compose config` 原文。

### 4.4 Tab: 环境变量

```
Card
|-- 分组 Select: [按主机] [项目通用]
|-- Key-Value 编辑列表: KEY | VALUE(可切换明文/掩码) | 敏感[默认开启] | [删除行]
|-- [+] 添加变量      [保存]
```

- VALUE 默认掩码显示（`text-sm` 圆点），创建时点击眼睛图标可临时查看。敏感开关默认开启；关闭前提醒此值将以非秘密配置写入 SQLite。
- 敏感变量仅创建时可查看，其值按 `docs/technical-architecture.md` 的凭据大小限制安全保存；SQLite 只存引用。若凭据管理器不可用，禁止保存敏感变量，不退回明文。明文日志、发布历史与配置预览中均不得出现变量值。
- 主机专属值覆盖项目通用值；重复键或保留键 `DEVINGPANEL_IMAGE` 在保存时提示冲突。发布时生成的 `.env` 仅放在版本化部署目录，权限 600，回滚前必须确认对应历史密钥仍可取回。

### 4.5 Tab: 目标主机

```
YAML 项目 Card
|-- 有序目标列表: 序号 | 主机组 Input | 主机别名 Input | [上移] [下移] [移除]
|-- [添加目标] [保存到 devingpanel.yaml]
|-- 组名/别名在本机缺失或不唯一: warning 提示，发布禁用
```

YAML 项目直接按文件顺序编辑 `deploy.targets`；每项以主机组和别名匹配本机主机，调整顺序即改变发布顺序。保存前核对目标绑定变化，必要时确认取消绑定主机的专属变量处理。原型中的未导入项目仍用“主机组 Select + 同组主机勾选表格”完成初次配置；发布页“更改”只调整本次发布目标。项目未绑定主机、配置待复核或合并校验失败时，[发布] 禁用并显示原因。

### 4.6 Tab: 发布历史

该项目维度的发布记录 Table：时间 | 发布标识 | 目标主机数 | 结果 | 耗时 | 操作([详情])。
点击详情跳转发布页对应记录。最近 20 条，分页 `Previous / Next`。

历史通过不可变项目 ID 关联，不以可编辑的项目名称关联；改名不影响项目历史，删除后重建同名项目不得继承旧历史。每页最多 20 条，页码及上一页/下一页的可用状态由实际记录数计算。
