# P3 项目列表 / 项目编辑 设计文档

> 需求映射：B-1 项目关联、B-3 构建参数、D-1 多 compose 文件、D-3 环境变量（SEC-4 写入远端 .env 权限 600）、M-1 绑定多主机

## 1. 页面目的

管理"项目"：本地代码目录、Dockerfile、compose 文件、构建参数、环境变量与目标主机的绑定关系。项目是发布的最小单元。

## 2. 入口

- 侧边栏"项目"；发布页选择项目。

### 3.2 新建项目 Dialog（sm:max-w-lg）

| 字段 | 控件 | 说明 |
|------|------|------|
| 项目名 | Input | 必填 |

创建后进入基本信息页签，在“本地代码目录”选择目录，再到构建配置中设置 Dockerfile 路径（初始为 `Dockerfile`）并完善其余配置；配置未完成时列表"状态"列显示 warning Badge"待完善"。列表菜单的 [编辑] 进入基本信息页签，不再单独提供详情入口或编辑弹窗。
若目录中没有 `devingpanel.yaml`，可在构建和 Compose 页签填写配置，首次完整保存时创建 v2 文件。目标主机在本机单独绑定；YAML 创建成功且目标绑定完成前不能发布。目录中已有该文件时读取并采用，不用新建表单覆盖。

### 3.3 导入开发者配置的项目

项目列表 [导入已配置项目] 选择包含 `devingpanel.yaml` 的本地代码目录。项目导入后可编辑构建和 Compose，保存结果写回项目文件。目标主机在本机绑定，不随 YAML 导入或写回。YAML 不存 SSH 密码、私钥或环境变量值；管理员须在本机预先配置目标主机、可信指纹和凭据。缺失时项目仍可导入，但不能发布。

```yaml
version: 2
name: myapp
tag: "{timestamp}"
builds:
  - service: web
    dockerfile: Dockerfile
    image: myapp
    platform: auto
    args:
      NODE_ENV: production
deploy:
  compose:
    files: [compose.yaml, compose.prod.yaml]
```

项目根目录是所有构建的 build context；每个 `builds` 条目须有唯一服务、镜像名及镜像变量，Compose 对应服务使用 `${DEVINGPANEL_IMAGE_WEB}` 等变量。Dockerfile 与 Compose 文件均为目录内相对路径，首个 Compose 文件在根目录。目标按本机绑定顺序发布；正式客户端把项目目标主机 ID 和顺序存入 SQLite，不写入 YAML。变更目标绑定时需管理员明确确认，可能清理取消绑定主机的本地专属变量。文件最大 64 KiB、UTF-8、单文档、`version: 2`，重复/未知字段、非法路径或格式一律报错。Build args 是明文，不可填写秘密。界面保存前校验完整清单与文件路径；若文件在编辑期间被外部修改则拒绝覆盖，需在基本信息中重新选择本地代码目录读取最新文件。发布前再读取 YAML 与本机目标绑定并冻结快照，不使用过期界面数据。文件丢失/损坏时不回退 SQLite 的旧值。

正式桌面客户端以 `devingpanel.yaml` 保存项目名、构建与 Compose 配置。项目由列表导入或新建后配置；目标绑定和普通环境变量存入本机 SQLite，敏感环境变量存入系统凭据管理器。多主机批次按目标顺序和并行度分波次执行；每波健康结果须逐目标确认，故障与未知状态在历史页单独核实。正式多主机 [开始发布] 在实机、视觉和混合架构验收完成前禁用。

原型保存和导入时检查镜像变量名是否唯一：服务名转成大写并将 `-` 替换为 `_` 后，`api-a` 与 `api_a` 会冲突。原型按文件顺序检查各服务的 `image` 字段覆盖结果；后续文件覆盖镜像变量时不能通过校验。正式客户端仍须按发布约定检查完整的 Compose 合并配置。

### 4.2 Tab: 构建配置

`devingpanel.yaml` v2 项目按 4.1 节编辑有序 `builds` 列表，每个服务各有 Dockerfile、镜像、平台和 Build args；不得把多个服务压成一个“部署服务”选择值。WebUI 在用户授权项目目录后实际读写 YAML 文件；远端构建和发布仍为演示。

字段区（不套外层 Card）：

| 字段 | 控件 |
|------|------|
| 构建服务 | 有序列表；每项包含唯一服务名、Dockerfile 相对路径和镜像名 |
| Tag 规则 | Input (mono)，支持 `{timestamp}` `{git-sha}` 占位，默认 `{timestamp}`；仅选择 `{git-sha}` 的项目需要 Git 仓库，生成发布标识后附架构后缀，构建前检查 tag 冲突，绝不覆盖旧版本 |
| 目标平台 | 每个构建项可选按主机自动（默认）/ linux/amd64 / linux/arm64；手选平台时所有已选主机必须匹配 |
| Build args | 每个构建项独立的 Key-Value 编辑列表（Add row） |

底部共用保存区提供 [保存] 和 [全部保存]；保存后 Toast 反馈。
正式客户端在使用 `{git-sha}` 时由内置 Go 库读取项目所属仓库的 `HEAD`，不要求本机安装 Git；普通非 Git 项目可正常使用默认 `{timestamp}`。若所选项目不是 Git 仓库或尚无提交，发布前提示修改 Tag 规则，不自动改用时间戳。`HEAD` 不包含未提交改动，预检时提示用户核对工作区。WebUI 原型仍只显示示例 SHA。
发布前通过 SSH 读取每台目标主机架构；自动模式汇总所需平台（如 `linux/amd64`、`linux/arm64`），客户端在开发机为每种架构各构建一次，为同一发布标识生成不同镜像 tag（如 `myapp:20261024-120000-amd64` 与 `myapp:20261024-120000-arm64`），同架构主机复用镜像。手选平台不匹配或本地 Docker 无法构建任一目标平台时，在上传前失败并提示本地构建环境需要的能力，不回退到 VPS 编译。Build args 不是秘密传输机制，编辑区提示不要填写密码或令牌。

### 4.3 Tab: Compose

文件增删和排序先修改草稿。[保存] 只提交 Compose 文件列表；[全部保存] 提交 YAML 草稿及本机目标绑定，规则见 4.1 节。原型未接入 SQLite。

```
Compose 字段区
|-- 说明行: "支持多个 compose 文件，按顺序合并（后者覆盖前者）"
|-- 文件列表 (可排序，每行):
|    1. docker-compose.yml          [本地路径, mono] [移除]
|    2. docker-compose.prod.yml     [+ 添加文件]
|-- [+] 添加 compose 文件 (系统文件选择器, 可多选)
```

交互：调整顺序用上移/下移按钮；文件不存在于本地时行内 warning 提示"文件不存在"。

发布约定（MVP）：

YAML v2 项目使用 3.3 节定义的服务专属镜像变量，如 `DEVINGPANEL_IMAGE_WEB`；每个 `builds` 项对应一个 Compose 服务和镜像变量。

- 允许一个或多个位于项目目录内的 Compose 文件，但**首个文件必须直接位于项目根目录**；后续文件可位于子目录。上传时保持相对于项目根目录的路径，开发机与 VPS 均以项目根目录为 Compose project-directory，固定 Compose 项目名，避免每次发布生成新的服务栈。生成的 `.env` 位于该次发布的版本化部署目录根（以项目根目录为基准），`env_file: .env` 因此按首文件所在根目录解析。
- 每个构建服务须通过自己的 `DEVINGPANEL_IMAGE_<服务名>` 变量引用本地构建镜像；客户端为每台主机填入匹配架构的镜像 tag（直连时为本地镜像名，Registry 模式为完整仓库地址）。其他服务可使用 VPS 已有或可拉取的现成镜像；部署前检查这些镜像是否可获取，缺失且无法拉取则报错，不因缺失而在 VPS 构建。
- `.env` 文件本身不能保证插值优先级：调用本地和远端 Compose 时，客户端必须从继承的进程环境中移除项目配置键与保留键，再以 `--env-file` 显式指向本次版本化根目录的 `.env` 提供项目值；服务专属镜像变量由客户端设置为该主机预期 tag，不能从用户环境继承。构建前与远端 `up -d` 前分别解析最终配置，确认所有构建服务的 `image` 均精确等于该主机预期 tag；配置原文可能含密钥，只在内存中校验且不得记录到日志。
- 发布前在每台主机对应环境变量下验证合并结果：所有服务都不得包含 `build`，否则阻止发布，避免 VPS 编译。仅上传 Compose 文件和客户端生成的 `.env`；普通相对 bind mount、除 `.env` 外的 `env_file`、本地文件型 `configs` / `secrets`、`include` / `extends` 及项目外路径不支持首版远端部署，检查到即明确报错；Windows 本地绝对路径不可作为 VPS 挂载路径，远端绝对挂载路径须由用户预先准备。不要静默改变路径指向。
- `.env` 仅提供 Compose 变量插值；要将变量注入容器，Compose 服务须在 `environment` 显式引用变量，或使用 `env_file: .env`。界面不展示可能含密钥的 `docker compose config` 原文。

## 草稿、保存错误与窄窗口原型

项目名、构建配置、Compose 文件和目标绑定分别保留草稿；列表与发布页使用已保存名称，列表状态也会标记未保存。存在草稿时，详情页显示“未保存”和“放弃修改”；放弃修改恢复这些配置的保存值。草稿未保存时禁用发布。

每次保存重新读取当前草稿。失败后保留输入并允许修正后重试；保存期间禁用重复提交，继续编辑的内容仍作为草稿保留。YAML 写入成功后才提交本次目标绑定。原型“全部保存”不提交环境变量值。

错误在详情页顶部汇总，并在对应字段标记、关联说明和定位首个错误；跨页签错误会定位相应配置页。环境变量页的“全部保存”遇到其他页错误时保留当前变量表单，显示错误汇总。文件错误包含相对路径及检查建议，不展示 YAML 内容或参数值。同一构建内禁止重复参数名，避免序列化时覆盖。

Build args、Compose 文件均有带行号的无障碍名称。窄窗口 Compose 路径占一行，排序/删除按钮另排；列表与历史在 1023px 及以下使用带字段名的分组行。当前页签自动出现在页签条可视范围。


## 编辑布局与保存位置（2026-11-27）

配置页共用底部保存区，保存按钮从各字段区移到此处，动作名称与保存范围不变。环境变量仍由环境变量表单取值；“全部保存”不包含变量值，YAML 写入期间继续保留用户后来输入的草稿。保存区随页面底部吸附，预留滚动空间，通知不遮挡或截获保存按钮。

字段区上限 800px；项目名和 Tag 上限 360px。宽度至少 1280px 时，右侧用 224px 辅助区显示当前草稿的构建、Compose 文件和目标数量，并提供项目文件状态与目标核对入口。窄窗口隐藏重复的辅助摘要，保留页头目录、状态、全部配置和保存操作。摘要随草稿更新，不因其变化重建输入控件。未保存改动不显示为就绪；示例项目仍沿用原型的演示就绪状态。

页签采用下划线选中态。发布历史保留完整字段，在表格容器不足 1080px 时改为分组记录。项目名修改仍以保存后的 YAML 为准，不改变历史归属规则。
